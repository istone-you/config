# git-commit-push

作業ツリーの変更を、`差分の確認 → ブランチ作成 → コミット → プッシュ` の順で安全に処理する。
各ステップは前のステップの結果に依存するため、必ず順番に実行し、内容を確認してから次へ進む。

Git リポジトリ内であることが前提。`git rev-parse --is-inside-work-tree` が失敗する場合は、その旨を伝えて中止する。

## Step 1: 差分の確認

まず何が変わったかを完全に把握する。この理解がブランチ名とコミットメッセージの根拠になる。

```bash
git status --short          # 変更・追加・削除ファイルの一覧（未追跡ファイル含む）
git diff                    # ステージ前の変更
git diff --staged           # 既にステージ済みの変更
```

- 差分が全く無ければ、コミットするものが無い旨を伝えて中止する。
- 変更内容を読み、「何を・なぜ変えたか」を一言で言えるレベルまで理解する。
- 意図しないファイル（ビルド成果物、秘密情報、デバッグ用の書き捨てなど）が混ざっていないか確認する。混ざっていれば、含めるかどうかをユーザーに確認する。

## Step 2: ブランチの作成

デフォルトブランチに直接コミットしない。現在地を確認してから分岐する。

```bash
git branch --show-current                                   # 今いるブランチ
git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null  # デフォルトブランチ（例: origin/main）
```

分岐の判断:

- **デフォルトブランチ（main / master 等）にいる場合**: 変更内容から新しいブランチを作る。
- **デフォルトブランチではない（既に作業ブランチにいる）場合**: 勝手に判断せず、必ずユーザーに確認する。以下の 3 択から選んでもらう。
  - **A. 今のブランチからさらに分岐して新しいブランチを作る**（今の作業ブランチを親にする）
  - **B. デフォルトブランチから新しくブランチを切る**（デフォルトブランチを親にする。今の作業ブランチのコミットは引き継がず、未コミットの変更だけを持って分岐する）
  - **C. ブランチ作成をスキップし、今のブランチのままコミットする**

  ユーザーの回答が得られるまで Step 3 に進まない。

ブランチ名は変更内容に基づき、リポジトリの既存の命名に合わせる。判断材料として既存ブランチを確認する:

```bash
git branch -a --sort=-committerdate | head -20
```

慣習が読み取れない場合の既定ルール:

- 英小文字の kebab-case。
- 変更の種類を接頭辞にする（`feat/`, `fix/`, `docs/`, `refactor/`, `chore/`, `test/` など）。例: `feat/add-autopairs`, `fix/markdown-preview`。

作成して切り替える。分岐元によってコマンドが変わる:

- **選択 A（今のブランチから分岐）** / **デフォルトブランチにいた場合**: 現在地を起点にする。
  ```bash
  git switch -c <branch-name>
  ```
- **選択 B（デフォルトブランチから分岐）**: デフォルトブランチを最新化してから、それを起点に分岐する。
  ```bash
  git fetch origin                                          # <default-branch>(origin/main 等)を最新にする
  git stash push -u                                         # 未コミット変更(未追跡ファイル含む)を退避
  git switch -c <branch-name> --no-track <default-branch>   # <default-branch> は上で調べた origin/main 等
  git stash pop                                             # 退避した変更を新ブランチへ適用
  ```
  - `--no-track`: 新ブランチをデフォルトに追跡させない（Step 4 の `push -u` で `origin/<branch>` を上流にするため）。
  - `stash push → pop`: 未コミット変更を新ブランチへ載せ替える。`pop` は**成功すれば退避エントリを自動削除**する。ただし退避した変更が「現在ブランチ↔デフォルトの差」と重なると `pop` で**衝突**し、そのときは退避エントリが**残る**ので、解決 → `git add` した後に `git stash drop` で消す。
- **選択 C（今のブランチのまま）**: ブランチは作らず、そのまま Step 3 へ進む。

## Step 3: コミット

変更をステージしてコミットする。

```bash
git add -A                  # 意図した変更のみを対象にする。除外したいものがあれば個別に add する
```

コミットメッセージは**リポジトリの慣習に必ず合わせる**。`git log --oneline -15` で言語・粒度・スタイル（日本語か英語か、命令形か体言止めか、接頭辞の有無など）を確認してから書く。

- 差分がまとまった一つの意図なら 1 コミット。無関係な変更が複数混ざるなら、意図ごとに `git add <paths>` で分けてコミットする。
- 件名は簡潔に「何をしたか」を書く。必要なら本文で「なぜ」を補足する。
- コミット署名トレーラー（`Co-Authored-By` 等）は、リポジトリの既存コミットが使っている場合のみ付ける。

```bash
git commit -m "<件名>"
```

## Step 4: プッシュ

外部に公開する操作なので、直前に「どのブランチを・どのコミットで push するか」を提示してから実行する。

```bash
git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null   # 上流の有無を確認
```

- 上流が未設定（初回 push）:

  ```bash
  git push -u origin HEAD
  ```

- 上流が設定済み:

  ```bash
  git push
  ```

push が拒否された場合（リモートが先行しているなど）は、勝手に `--force` せず、状況をユーザーに伝えて指示を仰ぐ。

## 完了報告

処理後に以下を簡潔に報告する:

- 作成／使用したブランチ名
- コミットのハッシュと件名
- push 先（`origin/<branch>`）と結果

## 注意事項

- デフォルトブランチへの直接コミット・直接 push はしない。
- `git add -A` の前後で対象ファイルを必ず確認し、意図しないファイルを巻き込まない。
- ブランチ名・コミットメッセージは必ずリポジトリの既存の慣習に合わせる（言語・接頭辞・粒度）。
- `--force` / `--force-with-lease` は、ユーザーが明示的に求めた場合のみ使う。
- PR 作成は本スキルの範囲外。求められたら別途対応する。
