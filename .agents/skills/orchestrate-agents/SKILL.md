# orchestrate-agents

受け取った 1 つの指示を、herdr の別パネルで動く複数のエージェントに委譲し、以下のパイプラインで進める。
このスキルを実行するエージェント自身は **オーケストレーター**（司令塔）に徹し、実作業（プラン/実装/レビュー）はすべて子エージェントに行わせる。

```
プラン作成 (claude) → プランレビュー (codex) 〔改訂ループ〕
  → ★ユーザー承認ゲート★
  → 実装 (cursor = agent) → 実装レビュー (codex と claude)
```

## 前提

- Herdr 内で動作する。まず `test "${HERDR_ENV:-}" = 1` を確認し、失敗したら Herdr 内ではない旨を伝えて中止する。
- herdr の CLI 操作（パネルの split / run / wait / read など）の正確な構文と作法は **`herdr` スキルに従う**。ここではその作法を前提に、オーケストレーションの流れだけを定義する。迷ったら `herdr --help` と各コマンド群の出力を正とする。
- 使用する実行ファイル:
  - プラン作成・実装レビュー: `claude`
  - プランレビュー・実装レビュー: `codex`
  - 実装: `agent`（cursor-cli。ユーザーの言う「cursor の agent コマンド」）
- 各エージェントは同じ作業ディレクトリ（同じリポジトリ）を共有する。成果物はファイル経由で受け渡す。

## 準備

1. 委譲する指示（タスク）を明確にする。曖昧なら着手前にユーザーへ確認する。
2. 受け渡し用の作業ディレクトリを 1 つ決め、以降すべて **絶対パス** で参照する（例: `/tmp/orchestrate-<短いスラッグ>/`）。Bash 呼び出し間で環境変数は保持されないため、パスは変数でなく実際の文字列で統一する。ここに各フェーズの成果物を置く:
   - `plan.md`（プラン）
   - `plan-review.md`（プランレビュー結果）
   - `review-codex.md` / `review-claude.md`（実装レビュー結果）

## パネル運用の共通作法

- **エージェントの identity ごとに 1 パネル**（claude 用・codex 用・agent 用）を用意し、後続フェーズ・改訂ループでも**同じパネルを使いまわして文脈を引き継ぐ**。例えばプランを書いた claude パネルはそのまま改訂・実装レビューにも使い、プランをレビューした codex パネルはそのまま再レビュー・実装レビューにも使う。これにより「なぜその設計にしたか」「前に何を指摘したか」という会話上の文脈が失われない。パネルの乱立も防げる。
  - ファイル受け渡し（`plan.md` 等）は成果物の正本として併用する。成果物の正＝ファイル、思考の連続性＝パネル、と役割を分ける。
- ユーザーのフォーカスは奪わない。分割は `herdr pane split --current --no-focus` を使い、方向は呼び出し元パネルの形状に合わせる（`herdr` スキルの geometry ルール準拠）。
- 作成したパネルには役割名を付ける（`herdr pane rename <id> "plan"` など）。パネル ID は必ず JSON レスポンスから読む。
- 起動〜指示〜完了待ち〜読み取りの基本サイクル:
  1. `herdr pane run <id> "<executable>"` で対話 TUI を起動する（引数でプロンプトを渡さない）。
  2. `herdr wait agent-status <id> --status idle` で入力可能になるのを待つ。
  3. `herdr pane run <id> "<プロンプト>"` で指示を送る。
  4. `herdr wait agent-status <id> --status working` → `--status done`（バックグラウンド時）で完了を待つ。実装は長時間かかるためタイムアウトを十分長く取る。
  5. `herdr pane read <id> --source recent-unwrapped --lines <n>` で結果を読む。成果物は原則ファイルに書かせ、ファイルを正とする。
- 待ちがタイムアウトしたら、`herdr pane get` と `pane read` で状態を確認する。`blocked`（承認待ち等）ならユーザーに状況を伝えて指示を仰ぐ。勝手に危険な承認を代行しない。
- 大きな成果物をプロンプト引数に貼り付けない。次のエージェントには `@<絶対パス>` のようにファイルを参照させる。
- **指示が「貼られただけ」で送信（Enter）されずに終わる事故に注意する。** プロンプトは必ず `herdr pane run`（テキスト＋Enter を一緒に送る）で送り、`send-text` だけで済ませない。送信後は入力欄に置かれただけになっていないかを必ず確認する: `herdr wait agent-status <id> --status working` で working へ遷移することを確認するか、`herdr pane read` で指示が実行に移ったことを確かめる。working にならず入力欄にプロンプトが残っている場合は、Enter（`herdr pane send-keys <id> Enter` 相当。正確な構文は `herdr` スキル／`herdr pane --help` を正とする）を送って確実にサブミットしてから次に進む。

## Phase 1: プラン作成 (claude)

`claude` パネルを用意し、指示を渡してプランをファイルに書かせる。コードは変更させない。

送るプロンプト例:

> 次の指示の実装プランを作成し、`/tmp/orchestrate-.../plan.md` に Markdown で書き出して。この段階ではコードは変更しないで。前提・変更方針・影響範囲・手順・懸念点を含めること。指示: 「<委譲する指示>」

完了後 `plan.md` を読み、プランの要点を把握する。

## Phase 2: プランレビュー (codex)

`codex` パネルを用意し、プランをレビューさせる。

送るプロンプト例:

> `@/tmp/orchestrate-.../plan.md` のプランをレビューして。問題点・抜け・リスク・改善提案を `/tmp/orchestrate-.../plan-review.md` に書き出して。実装はしないで。

`plan-review.md` を読む。**修正が必要な指摘がある場合**は Phase 1 の claude パネルに指摘を戻してプランを改訂させ、再度 codex にレビューさせる。この改訂ループは最大 2〜3 周までとし、収束しない／判断を要する場合はユーザーに要約して相談する。プランが妥当と判断できたら次へ進む。

## ユーザー承認ゲート（実装前・必須）

実装（コード変更）は安く戻せる最後の地点の直後にあり、また「ユーザーが本当に欲しいもの」との取り違えを潰せるのはここだけ。したがって **実装に入る前に必ずユーザーの承認を取る**。省略しない。

- 収束した最終プランの要点と、プランレビュー（codex）で反映した主な指摘を要約してユーザーに提示する。成果物ファイル（`plan.md` / `plan-review.md`）のパスも示す。
- ユーザーから次のいずれかを受け取るまで Phase 3 に進まない:
  - **承認** → 実装へ進む
  - **修正指示** → claude パネル（文脈保持済み）に戻してプランを直し、必要なら codex に再レビューさせ、あらためて承認を求める
  - **却下** → 中止し、理由をユーザーに確認する

## Phase 3: 実装 (cursor = agent)

ユーザーが承認したプランに従って `agent`（cursor-cli）パネルに実装させる。

送るプロンプト例:

> 承認済みのプラン `@/tmp/orchestrate-.../plan.md`（レビュー反映済み）に従って実装して。プランの範囲外の変更はしないこと。

実装は時間がかかるため完了待ちのタイムアウトを長めにする。途中で `blocked`（コマンド承認待ち等）になったら読み取って対応判断し、必要ならユーザーに確認する。完了後、`git status` / `git diff` で変更内容を把握する。

## Phase 4: 実装レビュー (codex と claude)

実装の差分を **codex と claude の両方** にレビューさせる。それぞれ既存の codex パネル・claude パネル（文脈保持済み）をそのまま使い、2 つは独立した観点として並行に走らせてよい（`herdr` スキルの並行実行の作法に従う）。

それぞれに送るプロンプト例:

> 現在の作業ツリーの差分（`git diff`）をレビューして。プラン `@/tmp/orchestrate-.../plan.md` を満たしているか、バグ・リグレッション・設計上の問題がないかを確認し、指摘を `/tmp/orchestrate-.../review-codex.md`（claude 側は `review-claude.md`）に書き出して。

両方の結果を読み、突き合わせて統合する。**ブロッカー級の指摘**があれば Phase 3 の実装パネルに戻して修正させ、再レビューする（このループも上限を設け、収束しなければユーザーに相談する）。

## 完了報告

ユーザーへ以下を簡潔に報告する:

- 最終的なプランの要点と、プランレビューで反映した主な指摘
- 実装された変更の概要（変更ファイル・要点）
- 実装レビュー（codex / claude）の結果と、残っている懸念・未対応事項
- 各成果物ファイルのパス

コミットやプッシュは本スキルの範囲外。必要なら別途 `git-commit-push` スキル等で対応する。

## 注意事項

- オーケストレーターは自分で実装・レビューを行わず、委譲・待機・突き合わせ・報告に徹する。
- 自分が作っていないパネル・ワークスペースは閉じない。このスキルで作ったパネルは、ユーザーが結果を確認できるよう原則残す（後片付けはユーザーの指示に従う）。
- 各フェーズの区切りで結果を要約し、次フェーズへ進む前に大きな方針転換が要る場合はユーザーに確認する。
- 子エージェントが破壊的操作の承認待ち（`blocked`）になった場合、内容を確認せず自動で承認しない。
